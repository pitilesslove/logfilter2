# 07. 기능 리스트 관리 규칙

## 개요

이 프로젝트의 모든 구현 작업은 **기능 리스트(Feature List)**로 추적한다.
기능 리스트는 계층적 작업 분해(WBS) 방식으로, 대기능 → 중기능 → 세부 작업으로 나누어 관리한다.

---

## ID 체계

| 레벨 | 형식 | 예시 | 설명 |
|------|------|------|------|
| Level 1 | `F{N}` | `F3` | 대기능 (Epic) |
| Level 2 | `F{N}.{M}` | `F3.2` | 중기능 (Feature) |
| Level 3 | `F{N}.{M}.{K}` | `F3.2.1` | 세부 작업 (Task) |
| Level 4+ | `F{N}.{M}.{K}.{J}` | `F3.2.1.1` | 하위 작업 (Sub-task) |

- 번호는 생성 순서대로 1부터 증가한다
- 한번 부여된 ID는 변경하지 않는다

---

## 상태 태그

각 작업 항목의 시작 부분에 `[태그]` 형식으로 표기한다.

### 진행 상태

| 태그 | 의미 |
|------|------|
| `[pending]` | 아직 착수하지 않음 |
| `[in-progress]` | 현재 진행 중 |
| `[done]` | 완료됨 |
| `[blocked]` | 다른 작업에 의해 차단됨 |

### 변경 태그

작업 도중 발견된 버그나 추가 구현 항목에 사용한다.

| 태그 | 의미 | 사용 시점 |
|------|------|----------|
| `[bug]` | 버그 발견 | 기존 작업에서 결함 발견 시 |
| `[fix]` | 버그 수정 | `[bug]` 항목을 해결하는 작업 |
| `[change]` | 기능 변경 | 기존 기능의 동작 변경 |
| `[add]` | 추가 구현 | 계획에 없던 새 항목 추가 |
| `[deprecated]` | 폐기됨 | 시나리오 변경으로 더 이상 불필요 |

### 상태 조합 예시

```markdown
- F3.2 [done] 가상 스크롤 구현 <!-- done: 2026-02-10 -->
- F3.4 [bug] 필터 변경 시 스크롤 위치 유실 <!-- found: 2026-02-11, → F3.4.1 -->
- F3.4.1 [fix] 뷰포트 중심 라인 기억 후 복원 <!-- fixes: F3.4 -->
- F5.3 [deprecated] WebSocket 전환 <!-- deprecated: 2026-02-12, 사유: SSE가 적합 → F5.4 -->
- F10.1 [blocked] 멀티 Pod 동시 조회 <!-- blocked: F8 완료 필요 -->
```

## 항목 작성 형식

```markdown
### F{N}. {대기능 이름}
> 참조: spec/{NN}-{name}.md | 파일: {수정 대상 경로}

#### F{N}.{M} [{상태}] {중기능 이름}
{설명 (1~2줄)}
<!-- 메타 정보: 날짜, 링크, 사유 등 -->

- F{N}.{M}.{K} [{상태}] {세부 작업}
  - F{N}.{M}.{K}.{J} [{상태}] {하위 작업}
```

### 필수 정보

| 항목 | 필수 | 설명 |
|------|------|------|
| ID | O | 고유 식별자 |
| 상태 태그 | O | 현재 진행 상태 |
| 작업 이름 | O | 무엇을 하는지 명확하게 |
| 참조 스펙 | 권장 | Level 1에 관련 스펙 문서 |
| 참조 파일 | 권장 | 수정 대상 파일 경로 |
| 의존성 | 해당 시 | `← F{N}` 형식으로 선행 작업 표기 |

## 불변 원칙 (Immutable + Append-Only)

**한번 작성된 항목은 수정하지도, 삭제하지도 않는다.**
유일하게 허용되는 변경은 **상태 태그 전환**뿐이다. 그 외 모든 변경은 **새 항목 추가**로 처리한다.

### 금지 행위

| 금지 | 이유 |
|------|------|
| 기존 항목의 설명 텍스트 수정 | 이력 추적 불가. 새 항목으로 추가해야 함 |
| 기존 항목 삭제 | 작업 이력 손실. `[deprecated]`로 표기 |
| 기존 항목의 ID 변경 | 참조 링크 깨짐 |
| 기존 항목의 참조/의존성 삭제 | 새 주석으로 보강만 가능 |

### 허용 행위

| 허용 | 방법 |
|------|------|
| 상태 태그 전환 | `[pending]` → `[in-progress]` → `[done]` (유일한 인라인 수정) |
| 주석 추가 | `<!-- done: 2026-02-15 -->` 등 메타 주석은 추가만 가능 |
| 새 하위 항목 추가 | 기존 항목 아래에 새 Level 추가 |
| 새 항목 추가 (`[bug]`, `[fix]`, `[add]`, `[change]`) | 관련 위치 아래에 새 줄로 추가 |

### 상황별 처리 방법

| 상황 | 처리 (모두 추가 방식) |
|------|----------|
| 작업 완료 | 상태를 `[done]`으로 전환 + `<!-- done: YYYY-MM-DD -->` 주석 추가 |
| 시나리오 변경으로 불필요 | 상태를 `[deprecated]`로 전환 + `<!-- deprecated: YYYY-MM-DD, 사유: {이유} -->` |
| 기능 내용이 바뀜 | 기존 항목 `[deprecated]` + 새 항목 `[change]`로 추가 + `<!-- replaces: F{N}.{M} -->` |
| 버그 발견 | 새 `[bug]` 항목 추가 + `<!-- found: YYYY-MM-DD -->` |
| 버그 수정 | 새 `[fix]` 항목 추가 + `<!-- fixes: F{N}.{M} -->` |
| 추가 작업 발견 | 새 `[add]` 항목 추가 |
| 다른 작업과 연관 | `<!-- link: F{N}.{M} -->` 주석 추가 |

## 파일 구조 및 이관 규칙

### 기본 파일

```
spec/
├── features.md                  # 메인 기능 리스트 (마스터 인덱스)
└── features/                    # 이관된 Level 1 상세 파일
    ├── F01-server-setup.md      # (이관 예시)
    ├── F02-log-parsing.md
    └── ...
```

### 이관 조건

다음 중 하나라도 해당하면 해당 Level 1을 별도 파일로 분리한다:

1. **Level 1이 `[done]`으로 완료됨** — 완료된 작업을 아카이브하여 메인 파일을 가볍게 유지
2. **features.md가 300줄을 초과** — 가독성 유지를 위해 가장 큰 Level 1부터 분리
3. **Level 2 이하 항목이 20개를 초과** — 해당 Level 1의 복잡도가 높아 별도 관리 필요

### 이관 방식

1. 해당 Level 1의 전체 내용을 `spec/features/F{NN}-{name}.md`로 이동
2. 메인 `features.md`에는 요약 한 줄 + 파일 링크만 남김:
   ```markdown
   ### F1. Express 서버 구축 [done]
   > 상세: [spec/features/F01-server-setup.md](features/F01-server-setup.md)
   <!-- done: 2026-02-10, 이관: 2026-02-12 -->
   ```

## 작업 흐름

### 새 작업 시작

1. `features.md`에서 다음 `[pending]` 작업 확인 (의존성 충족된 것)
2. 해당 항목의 상태 태그만 `[in-progress]`로 전환
3. 작업 수행
4. 완료 시 상태 태그를 `[done]`으로 전환 + `<!-- done: YYYY-MM-DD -->` 주석 추가

### 버그 발견 시

1. 관련 항목 아래에 **새 줄로** `[bug]` 항목 추가 (기존 항목은 건드리지 않음)
2. 수정이 필요하면 **새 줄로** `[fix]` 항목도 추가
3. 수정 완료 후 `[bug]`와 `[fix]` 상태를 `[done]`으로 전환

### 계획 변경 시

1. 기존 항목의 상태를 `[deprecated]`로 전환 + 사유 주석 추가 (내용 수정 금지)
2. **새 항목을** `[change]` 또는 `[add]` 태그로 추가
3. 필요 시 링크 주석 추가 (`<!-- replaces: F{N}.{M} -->`)

### Level 1 완료 시 이관

1. 해당 Level 1의 모든 하위 항목이 `[done]` 또는 `[deprecated]`인지 확인
2. 전체 내용을 `spec/features/F{NN}-{name}.md`로 **복사** (원본은 유지)
3. `features.md`의 해당 Level 1을 요약 한 줄 + 파일 링크로 **교체**:
   ```markdown
   ### F1. Express 서버 구축 [done]
   > 이관됨: [spec/features/F01-server-setup.md](features/F01-server-setup.md)
   <!-- done: 2026-02-10, 이관: 2026-02-12 -->
   ```
4. 이관된 파일에서도 불변 원칙은 동일하게 적용된다
